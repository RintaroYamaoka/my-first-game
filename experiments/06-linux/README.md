# 実験 5: 同梱する小さな Linux

問い(`docs/decisions/0001`): ゲームに同梱した Linux を、プレイヤーの PC の上で、速く・確実に動かせるか。

## 作ったもの

| もの | 中身 |
|---|---|
| `image/Dockerfile` | Linux の組み立て方。Alpine Linux 3.24.4 から、カーネル(`linux-virt`)と、中身(bash、git、Node.js 24、vim、nano)を取り出す |
| `image/init`、`inittab`、`boot.sh` | 起動の手順。直列の線(シリアル)にシェルを出す |
| `image/bench.sh` | よく使う操作の時間を測る |
| `build.sh` | 組み立てて `target/linux-image/` に置く(Docker が要る) |

できあがるのは 2 つのファイルだけ。**カーネル 12 MB + 中身 47 MB**。中身はすべてメモリの上で動く(ディスクを使わない)。

Linux を動かすのは QEMU。ゲームのターミナル(`experiments/05-terminal/`)は、QEMU を起動して、その直列の線につながる。

```sh
./experiments/06-linux/build.sh
cargo run -p terminal -- experiments/01-world-from-code/sample --linux target/linux-image --accel kvm
```

`--accel` は、QEMU が Linux を動かす方式。

| 方式 | 意味 |
|---|---|
| `tcg`(既定) | CPU をソフトウェアで真似る。どの PC でも動く。遅い |
| `kvm`(Linux)/ `whpx`(Windows) | PC の仮想化の機能を使う。速い。Windows では「Windows ハイパーバイザー プラットフォーム」という機能を、管理者がオンにする必要がある |

## 測った結果(WSL の上の Docker の中の QEMU 11.0.3、2026-11-17)

| 操作 | tcg(真似る) | kvm(仮想化の機能) |
|---|---|---|
| 起動(カーネルから、シェルが出るまで) | 約 5 秒 | 約 1〜2 秒 |
| `ls`、`bash`、`grep -r` | 0.05 秒 | 0.01 秒 |
| `git init` / `add` / `commit` | 0.1〜0.3 秒 | 0.01 秒 |
| `node`(console.log だけ) | **1.8〜2.5 秒** | 0.2 秒 |
| TypeScript のファイルを実行 | **4.4 秒** | 0.4 秒 |
| メモリ | 60 MB | 80 MB |

## Windows で測った結果(Windows 用の QEMU 11.1.0、RTX 5070 Laptop の PC、2026-11-17)

| 操作 | tcg(真似る) | whpx(仮想化の機能) |
|---|---|---|
| 起動(カーネルから、シェルが出るまで) | 約 6 秒 | 約 2 秒 |
| `ls`、`bash`、`grep -r` | 0.05〜0.1 秒 | 0.01 秒 |
| `git init` / `add` / `commit` | 0.1〜0.2 秒 | 0.01 秒未満 |
| `node`(console.log だけ) | **1.7〜3.3 秒** | 0.07〜0.3 秒 |
| TypeScript のファイルを実行 | **4.2 秒** | 0.2 秒 |

Windows でも両方の方式で動いた。速さの傾向は WSL 側と同じ。この PC は、仮想化の機能(whpx)が使えた。

## 分かったこと

- **動く。** ゲームのターミナルから、同梱用の Linux の中でコマンドを打てた(WSL の窓で、画面を撮って確認)。
- **シェルと git は、遅い方式でも十分に速い。**
- **Node.js は、遅い方式だと 1 回の実行に 2〜4 秒かかる。** 速い方式なら 0.2〜0.4 秒。
  → 「誰の PC でも、設定なしで速い」は、QEMU だけでは満たせない。これが、この実験で見つかった一番大きな問題。
- Node.js の TypeScript の実行は、`import "./config"` のように拡張子を省いた書き方を解決できない。
  見本のコードの書き方か、実行の道具を決める必要がある。

## 本人が Windows で触った結果(2026-11-17)

- Ctrl+C で、動いているコマンド(`sleep 100`)を止められた(合図が QEMU に横取りされず、中の Linux に届く)
- ターミナルの上でクリックができず、コピーができないのは不便 → マウスでの選択・コピー・貼り付けを `05-terminal` に入れた

## ゲームと Linux の間の通り道(2026-11-18 に変更)

最初は、QEMU を擬似端末の中で動かし、画面入力(標準入力)経由で文字を送っていた。Windows では、これに 2 つ問題があった。

- まとめて送った文字(貼り付け)が、8 文字までしか届かない(Windows 版の QEMU の、標準入力の読み方の限界)
- 貼り付けだと知らせる印(bracketed paste)を付けると、Windows の擬似端末(ConPTY)が丸ごと捨てる

そこで、**ゲームが TCP の口(127.0.0.1 の空いている番号)で待ち、QEMU の直列の線をそこへつなぐ** 形に変えた。
QEMU は、窓を出さない子プロセスとして動く。Windows で、貼り付け・41 文字の一括送信・日本語が、欠けずに届くことを確認した。

## 遅い方式でも、Node.js を待たずに使えるか(2026-11-18、`bench=2`)

Node.js を起動したままにして、実行するファイルだけを頼む形(`image/runner.mjs`)を測った。

| やり方 | tcg(真似る) | kvm(仮想化の機能) |
|---|---|---|
| 毎回 `node` を起動する | 2.5〜3.3 秒 | 0.1 秒 |
| 起動したままの Node.js に頼む(同じプロセスの中で読み込む。前の実行の状態が残る) | 1 回目 1.7 秒、2 回目から **0.2 秒** | 0.01 秒 |
| 起動したままの Node.js に頼む(別スレッドで、毎回まっさらな状態で実行する) | **1.5 秒** | 0.08 秒 |

- 起動したままにすると、遅い方式でも半分ほどになる。ただし、毎回まっさらな状態で実行する(本物と同じ振る舞い)なら 1.5 秒かかる
- 0.2 秒まで縮むのは、前の実行の状態が残るやり方だけ。本物の `node` と振る舞いが変わるので、そのままは使えない
- **結論: 工夫で遅い方式を「速い」にはできない。気持ちよく遊ぶには、仮想化の機能(Windows では whpx)が要る。**
  遅い方式は「動くが、Node.js は待たされる」予備として残す

## Rust モード(2026-11-18、`bench=3`)

プレイヤーが書く言語は、基本が TypeScript、加えて Rust モード(`docs/concept.md`)。Rust を入れた Linux も測った。

```sh
EXTRA="rust cargo" TAG=-rust ./experiments/06-linux/build.sh   # target/linux-image-rust/
```

| | Rust なし | Rust 入り(rustc 1.96.1) |
|---|---|---|
| 中身の大きさ | 47 MB | **279 MB** |
| 起動(kvm / tcg) | 約 1〜2 秒 / 約 5 秒 | 約 6 秒 / 約 17 秒 |

| 操作 | tcg(真似る) | kvm(仮想化の機能) |
|---|---|---|
| `cargo build`(最初の 1 回、hello world) | 7.0 秒 | 0.4 秒 |
| `cargo build`(コードを書き換えたあと) | **11.6 秒** | 0.75 秒 |
| `cargo build`(1 行だけ変えたあと) | 3.0 秒 | 0.3 秒 |
| `cargo check`(型の確認だけ) | 2.0 秒 | 0.1 秒 |
| `cargo run`(作り直しなし) | 0.6 秒 | 0.03 秒 |

- **仮想化の機能があれば、Rust モードも速い**(書き換えて 1 秒以内に動く)
- **遅い方式では、Rust モードは実用にならない**(書き換えるたびに 3〜12 秒)。Node.js よりも差が大きい
- 中身がすべてメモリに載る今の作りだと、Rust 入りは起動が遅く、メモリも多く要る(測定では 3 GB を割り当てた)。
  Rust の道具は、メモリに載せずにディスクから読む形に変える必要がある(未検証)

## ファイルの変化を、世界へ知らせる(2026-11-18)

ターミナルでファイルを作る・書き換える・消すと、世界が変わる。このゲームの中心の仕組みを、初めて端から端まで通した。

| 部分 | 役目 |
|---|---|
| `image/agent.sh`(Linux の中の見張り番) | `/root/sample` を見張り(inotify)、変化を 2 本目の直列の線(ttyS1)へ 1 行ずつ書く。起動時には、全部のファイルを送る |
| `05-terminal/src/terminal.rs` の `watch_files` | 知らせを読んで、この PC の上の写し(一時フォルダ)に反映する |
| `05-terminal/src/main.rs` の `resync` | 写しが変わったら、世界を作り直す。今いる世界は、名前でたどり直す |

知らせの形: `F <中身(base64)> <道筋>`(できた・変わった)、`D <道筋>`(消えた)、`S`(一区切り)。

WSL の窓で確認: `seq … > src/tower.ts` で高い柱が立ち、`rm src/store.ts` で柱が消えた。

分かったこと・残り:

- 世界は、変化のたびに丸ごと作り直している。作り直す前と後の形を名前で対応づけて、動きにしている:
  変化が起きた場所へ視線が向く → 向き終わってから、新しい柱は足元から伸び、消えた柱は足元へ沈む。他の柱は、前の場所から今の場所へ動く
- 本人の判断(2026-11-18): 動きの順番(向いてから、動く)だけを前提として残す。速さ・色・形の作り込みは、今はしない
- 写しを経由するので、世界を組み立てる部分(実験 1〜2c)は、そのまま使えた
- 一時フォルダの写しは、終了時に消していない

## 多層構造: コンテナの中に、コンテナを作る(2026-11-18)

問い(`docs/decisions/0001`): コンテナの中にコンテナを入れた多層構造が、同梱の Linux の上で動くか。

```sh
ROOT=rootfs-layers TAG=-layers ./experiments/06-linux/build.sh   # Docker 入り(target/linux-image-layers/)
docker run --rm --device /dev/kvm my-first-game-linux:bench-layers qemu-system-x86_64 -accel kvm -cpu host -m 2048 -smp 2 \
  -nographic -no-reboot -kernel /out/vmlinuz -initrd /out/initramfs.gz -append "console=ttyS0 quiet bench=4"
```

**動いた。3 層とも。** Linux 本体(1 層目)の中で Docker を動かし、コンテナ(2 層目)を起こし、
その中でもう一つ Docker を動かして、コンテナ(3 層目)を起こした。本物の `docker exec` を 2 段重ねて、3 層目に入れた。

| 操作 | tcg(真似る) | kvm(仮想化の機能) |
|---|---|---|
| 起動(カーネルから、シェルが出るまで) | 14.5 秒 | 3.1 秒 |
| Docker が使えるようになるまで | 12.2 秒 | 0.5 秒 |
| コンテナの元(イメージ、110 MB)を用意する | 38.7 秒 | 3.9 秒 |
| 2 層目を起こす(`docker run`) | 5.4 秒 | 0.2 秒 |
| 2 層目に入ってコマンド(`docker exec … hostname`) | 1.2 秒 | 0.08 秒 |
| 2 層目で Node.js | 4.4 秒 | 0.13 秒 |
| 3 層目のための Docker が使えるようになるまで | 8.2 秒 | 0.5 秒 |
| 3 層目を起こす | 3.4 秒 | 0.3 秒 |
| 3 層目に、外から 2 段で入る(exec → exec) | 1.6 秒 | 0.27 秒 |
| 3 層目で Node.js | 3.8 秒 | 0.43 秒 |

大きさとメモリ:

| | いつもの中身 | Docker 入り |
|---|---|---|
| 中身(initramfs) | 47 MB | 203 MB(Docker とカーネルの部品で 約 126 MB、イメージの元で 約 30 MB) |
| 使ったメモリ(3 層を動かした状態) | — | 約 1 GB(中身がメモリに載るぶんが大半)。2 GB の割り当てで動いた |

仕組みで気をつけたこと:

- 外(インターネット)からイメージを取ってこられない。組み立てるときに小さな中身(`box.tar`)を用意して、中で `docker import` する
- 中身がメモリの上にあるので、Docker に `DOCKER_RAMDISK=true` を渡す(根の入れ替え方を変える)
- 3 層目の Docker の道具は、Linux 本体のものを読み取り専用で見せている(同じものを二重に持たないため)

分かったこと・残り:

- **仮想化の機能があれば、多層構造は速い**(どの操作も 0.5 秒以内)。なければ、どの操作も 1〜5 秒かかり、準備に 1 分以上かかる
- イメージを用意する時間(3.9 秒)は、起動のたびにかかる。中身をメモリではなくディスクに置けば、1 回で済む(未検証。Rust モードの課題と同じ)
- 1 回目の測定で、WSL ごと落ちた(3 GB を割り当て、546 MB のイメージを 2 回作っていた)。原因は特定できていない。負荷を下げた 2 回目・3 回目は落ちなかった
- Docker は大きい(中身が 4 倍)。ゲームが必要とするのが「層に潜る体験」だけなら、もっと小さい道具で足りるかもしれない(未検討)
- `ssh` で潜る形、Windows(whpx)での動作は、まだ確かめていない

## まだ確かめていないこと

- 仮想化の機能がオフの PC での振る舞い(自動で遅い方式に切り替える、案内を出す、など)
- ライセンスの整理(QEMU は GPL。別のプログラムとして同梱する。`docs/decisions/0002`)
