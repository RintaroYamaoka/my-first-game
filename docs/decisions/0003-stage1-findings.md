| 同梱した Linux を、Windows の上で動かせるか | できる | 実験 5 |

**結論: コンセプトは、技術的に成立する。** ただし、条件が 1 つ付く(下の 1)。

## 決めたこと

### 1. 仮想化の機能を、必須にするか

測った数字(速い方式 / 遅い方式):

| 操作 | 仮想化の機能あり | なし |
|---|---|---|
| Node.js を 1 回動かす | 0.07〜0.3 秒 | 1.7〜3.3 秒 |
| Rust のコードを書き換えて作り直す | 0.3〜0.75 秒 | 3〜12 秒 |
| コンテナを起こす | 0.2〜0.3 秒 | 5 秒 |
| コンテナの準備(起動のたび) | 4 秒 | 1 分以上 |

Windows では「Windows ハイパーバイザー プラットフォーム」という機能で、管理者がオンにして、再起動する必要がある。

**決定(本人、2026-11-18): 必須にする。**「必須にしなければいけないのではないでしょうか。仮想化は必須の方がいいと思います」
オフの PC では、起動時に、オンにする手順を案内する(作り方は未定。遅い方式を逃げ道として残すかも未定)。

- 理由: 遅い方式では、ゲームの芯(命令が効いて、世界がすぐ応える)が成り立たない
- 代償: 買った人の一部は、最初に設定と再起動が要る。ストアページの「必要な環境」に書く必要がある。
  会社の PC など、自分で設定を変えられない人は遊べない
- まだ分からないこと: オンになっている PC の割合。機能そのものが使えない PC(古い CPU、Windows の Home 版での扱い)

### 2. プレイヤーが書く言語

**決定(本人、2026-11-18): TypeScript と Rust の、両方を選べるようにする。** どちらかを「基本」「上級者向け」と分けない。
仮想化の機能があれば、どちらも 1 秒以内に動く。Rust の道具は大きい(中身が 47 MB → 279 MB)ので、ディスクに置く(下の 4)。

### 3. 層を作る道具

Docker は動いたが、大きい(中身が 47 MB → 203 MB、3 層でメモリ約 1 GB、準備に毎回 4 秒)。

**決定(本人、2026-11-18): まだ決めない。あとで試す。** 段階 3(遊びの試作)で、ミッションが実際に必要とするものを見てから決める。
本物の `docker` コマンドを打てること自体が遊びの中身なら Docker。「層に潜る体験」だけが要るなら、もっと小さい道具(名前空間を直接使う、など)。

### 4. Linux の中身の置き場所

**決定(本人、2026-11-18): メモリに置く形と、ディスクに置く形を比べて、軽い方を採用する。** 比べた結果、**ディスクに置く形を採用する。**

比べた 2 つの形:

- メモリに置く形: 中身を丸ごと 1 つのファイル(initramfs)にして、起動時にすべてメモリへ広げる
- ディスクに置く形: 中身を、圧縮した読み取り専用のファイル(squashfs)にして、ディスクとしてつなぐ。使うところだけ読む。書き込みは、メモリの上の層へ

測った結果(速い方式。WSL 側の kvm。`experiments/06-linux/compare.py`):

| 中身 | 置き場所 | 起動(QEMU の起動からシェルまで) | QEMU が使ったメモリの最大 | ファイルの大きさ |
|---|---|---|---|---|
| いつもの | メモリ | 1.9 秒 | 374 MB | 60 MB |
| いつもの | **ディスク** | **1.3 秒** | **241 MB** | 56 MB |
| Rust 入り | メモリ | 10.1 秒 | 1,435 MB | 292 MB |
| Rust 入り | **ディスク** | **1.5 秒** | **677 MB** | 258 MB |
| Docker 入り | メモリ | 5.1 秒 | 1,061 MB | 216 MB |
| Docker 入り | **ディスク** | **1.8 秒** | **251 MB** | 195 MB |

Windows(whpx)でも同じ傾向: Rust 入りの起動が 14.6 秒 → 9.0 秒(うち Linux の中の起動は 12.0 秒 → 1.0 秒)、
Linux の中で使っているメモリが 982 MB → 114 MB。

ディスクに置く形の代償は 1 つ: **最初の 1 回だけ、ディスクから読むぶん遅い。** 2 回目からは同じ速さ。

| 操作 | メモリ | ディスク(最初の 1 回) | ディスク(2 回目) |
|---|---|---|---|
| Node.js を 1 回動かす(kvm) | 0.07 秒 | 0.5〜0.7 秒 | 0.06〜0.12 秒 |
| Node.js を 1 回動かす(Windows) | 0.13〜0.28 秒 | 1.2 秒 | 0.1 秒 |
| `cargo build`(kvm) | 0.55 秒 | 3.1 秒 | 0.2 秒 |
| `cargo build`(Windows) | 0.33 秒 | 4.5 秒 | 0.23 秒 |

残り: プレイヤーが作ったものを保存する、書き込める置き場所(今は、書き込みはメモリの上で、終了すると消える)。
最初の 1 回の遅さは、起動の裏で先に読んでおけば隠せる見込み(未検証)。

## 段階 1 のコードの扱い

`docs/roadmap.md` のとおり、実験のコードは捨てる前提。残すのは、分かったこと(各実験の `README.md`)と、次の仕組みの形:

- 世界は、本物の状態の「写し」から組み立てる。作り直す前と後を名前で対応づけて、動きにする
- ゲームと Linux は、ローカルの通信でつなぐ(1 本はターミナル、1 本は状態の知らせ)
- 音は、鳴らしっぱなしの声に、毎コマ値を書き込む
- 変化が起きたら、そちらを向いてから、形が動く(本人の決定、2026-11-18)
