# 開発ロードマップ

最終更新: 2026-11-15(アイデア出しと、音・演出の扱いを組み直した)

目標: **Steam で配信し、有名になることも目指せるインディーゲームを、品質に妥協せず作る。**

## 4つの原則

1. **アイデアは出し切ってから絞る。** 出している間は「作れるか」「大変か」で削らない。
   絞るのは出し切った後に、芯に合うかどうかで行う
2. **音と演出は芯。最初から試す。** このゲームでは、音と演出は飾りではなく「潜る感覚」そのもの。
   早い段階の試作から入れる。後回しにするのは、量を作る作業だけ
3. **面白さと気持ちよさを確かめてから、量を作る。** 1つの瞬間・1本のミッションを納得いくまで
   磨いてから増やす。量を先に作ると、後で全部を直すことになる
4. **品質は、範囲を削って守る。** 時間が足りないときは質を下げず、量(ミッション数、機能)を減らす

各段階には通過条件を置く。満たすまで次へ進まない。

## 全体図

| 段階 | 問い | 作るもの | 通過条件 |
|---|---|---|---|
| 0. 構想 | 何を作りたいのか | アイデアの山 → 選んだ核 | 本人が出し切ったと言える。核になるアイデアが選べている |
| 1. 技術検証 | 作れるのか | 動くだけの実験 | 本物の環境に潜り、世界が本物から組み上がる |
| 2. 瞬間の試作 | 気持ちいいのか | 見せ場ごとの小さな試作(音と演出つき) | 本人が「これだ」と言える瞬間が揃う |
| 3. 遊びの試作 | 面白いのか | 潜る1本・築く1本を通して遊べる形 | 初見の人が遊び、もう1本やりたいと言う |
| 4. 世界づくり | どんな世界か | 見た目・音・物語の基準 | 基準の絵と音と物語の骨子が揃う |
| 5. 完成見本 | 製品の品質に届くか | 15〜30分ぶんの製品品質 | 見た人が欲しいと言う。全体の作業量が見積もれる |
| 6. お披露目 | 欲しい人はいるか | ストアページ、予告動画、体験版 | ウィッシュリストが目安に届く |
| 7. 量産 | 最後まで作れるか | 全ミッションと物語 | 最初から最後まで通して遊べる |
| 8. 仕上げ | 売り物として出せるか | 調整済みの完成版 | 致命的な不具合がなく、審査を通る |
| 9. 発売と発売後 | — | 発売、更新 | — |

**現在地: 1 に入った(2026-11-16)。** 構想は、言葉と Web の試作で決められる範囲が固まった。0 と 2 には、必要になったら戻る。

段階は一直線ではない。0・1・2 は行き来する(下の「0〜2 の回し方」)。

## 0〜2 の回し方

```
   0. 構想  ──アイデア──▶  2. 瞬間の試作
      ▲                        │
      └──── 触って出た新しいアイデア ◀──┘

   1. 技術検証  ──「本物でここまでできる」──▶  0 と 2 に返す
```

- アイデアは、触れる形にすると膨らむ。良さそうなものは 2 ですぐ試作にして、触って、また 0 に戻る
- 1 は 0 と並行できる。本物の環境で何ができるかが分かると、アイデアの材料が増える

## 各段階

### 0. 構想

**発散** → **収束** の2つに分ける。

発散(今ここ):

- 本人が思いついた順に話す。断片のままでよい
- すべて `docs/ideas.md` に記録する。この間は削らない
- 切り口: 場面、音、演出、世界、人物、物語、ミッション、仕組み
- 似たゲーム・映画・音楽に触れて、良い点と不満を書き出すのも材料になる

収束(出し切った後):

- アイデアを「芯」「あると良い」「今回は見送る」に分ける。基準は `concept.md` の芯に合うか
- 選んだ核を `concept.md` に反映する
- **誰のためのゲームか**を決める(コマンドを知らない人も遊べるようにするのか)
- **一言で伝わる売り**を決める(予告動画の最初の数秒で見せる場面)

見送ったアイデアは消さない。続編や更新の材料になる。

### 1. 技術検証

「そもそも作れるか」を確かめる。成立しなければコンセプトが崩れる。0 と並行できる。

- ゲームに同梱した小さな Linux を、Windows 上で動かす(QEMU か v86)
- その中に多層構造(サーバーの中のコンテナ)を作り、本物の `ssh` や `docker exec` で潜る
- 本物の `ls` や `ps` の結果から、世界を組み立てる
- 書いたコードを本物として動かし、世界に現す(築く側)
- Rust + Bevy で、本物のターミナルの内容を表示し、キー入力を遅れなく通す(`decisions/0002`)
- `prototypes/dive/` と同じ場面を Bevy で作り、起動時間・メモリ・動きの滑らかさを測る
- 演出の数値を、動かしたまま調整できる仕組みを作る
- Steam との連携(実績、オーバーレイ)が動くかを見る
- 同梱する部品のライセンスが有料配信で問題ないか

見た目は雑でよい。ここで作ったコードは捨てる前提。

### 2. 瞬間の試作

ゲームの見せ場を1つずつ取り出し、**音と演出を付けて**小さく作る。1つ数日。

見せ場の例(0 で増える):

- 下の層へ落ちる瞬間
- 上の層へ引き戻される瞬間
- 命令が効いて世界が変わる瞬間
- 書いたコードが世界として立ち上がる瞬間
- 失敗した瞬間、見つかった瞬間
- 深い層にいるときの空気

試すこと: 動きの速さと間、カメラ、光と色、音の高さ・速さ・質感、文字の出方、操作との噛み合い。

`prototypes/dive/` が最初の1つ。ここは何度でも作り直す。納得いくまで次へ進まない。

### 3. 遊びの試作

2 で作った瞬間をつなぎ、潜るミッション1本と築くミッション1本を通して遊べる形にする。
背景や建物はまだ単純な形でよい。音と演出は 2 のものを入れる。

- 遊びの芯(調べる → 見つける → 変える → 世界が応える)が面白いか
- 難しさは適切か。詰まったときに何が助けになるか
- **自分以外の人に遊んでもらう。** 横で黙って見る。説明したくなった箇所が直す箇所

通過できなければ、遊びを作り直す。

### 4. 世界づくり

量産の前に「基準」を1つずつ作る。以後の絵と音は、すべてこの基準に合わせる。

- **見た目**: 基準になる画面を1枚、完成品質で作る(質感、光、色、文字)
- **音**: 基準になる曲と効果音。音全体の設計(深さで音がどう変わるか、無音の使い方)
- **演出**: 2 で決めた瞬間を、基準の見た目と音で作り直す
- **物語**: 舞台、主人公、依頼主、全体の筋の骨子
- **経営の層**: 報酬、成長、解放の設計
- **対応する言語**: 日本語と英語を出すか。文章の量に響くので早く決める
- **自作と外注の線引き**: 絵・3D・音楽・効果音のどこを自分で作り、どこを買うか頼むか。予算もここで決める

### 5. 完成見本

ゲームの一部分(依頼を受ける → 潜る → 解決 → 報酬)を、製品と同じ品質で最後まで作る。

- これが予告動画とストアページの素材になる
- かかった時間から、全体の作業量を初めて見積もれる
- 全部を入れようとしない。ゲームを代表する一部分でよい

### 6. お披露目

- Steam のストアページを公開し、ウィッシュリストを集め始める
- 予告動画を出す
- 体験版を出し、Steam Next Fest(体験版の催し)に参加する。発売前の最後の回に出るのが定石

### 7. 量産

完成見本と同じ型で、ミッションと物語を増やす。新しい仕組みはなるべく足さない。

### 8. 仕上げ

- 多くの人に遊んでもらい、難易度と分かりやすさを調整する
- 音の最終調整(全体の音量の釣り合い、さまざまなスピーカーとヘッドホンでの確認)
- 不具合の修正、動作の軽さ、さまざまな PC での動作確認
- 翻訳、実績、セーブの確認、Steam の審査

### 9. 発売と発売後

発売、不具合の修正、反応を見た更新。

## 並行して進める線

段階とは別に、途中から最後まで続くもの。

| 線 | 始める時期 | 内容 |
|---|---|---|
| アイデア | 0 から最後まで | 思いついたら `ideas.md` に足す。収束の後に出たものは「見送る」に入れて、段階の切れ目で見直す |
| 音と演出 | 0 から | 0 でアイデア → 2 で試す → 4 で基準 → 5 で製品品質 → 7 で量 → 8 で最終調整 |
| 試遊 | 3 から | 節目ごとに人に遊んでもらう |
| 発信 | 2 から | 瞬間の試作を動画や画像で出す。見てくれる人を少しずつ増やす |
| 物語 | 0 から | アイデア → 4 で骨子 → 5 で1話 → 7 で全体 |

## 数字の目安

マーケティング系の記事にもとづく目安で、公式の基準ではない。記事によって数字が違う。

- 発売時のウィッシュリストは **5,000〜10,000** が一つの目安とされる(よく挙がるのは約 7,000)
- 発売前のウィッシュリストの大半は、発売の 4 か月以上前に集まるという調査がある。
  ストアページは早く出すほうがよい
- Steam Next Fest で得られる数は、参加前に持っていた数と強く関係する

Valve は「表示されるために必要な最低数はない」としている。

## 期間

**まだ見積もれない。** 完成見本(5)ができて初めて、全体の作業量が分かる。
先に日程を決めると、品質か範囲のどちらかを無理に合わせることになる。

## 役割

- **本人**: アイデアを出す。何が面白いか、何が美しいか、何が気持ちいいかを決める。人に見せて反応を見る。発信する
- **Claude**: アイデアを記録して膨らませる。調査、設計の案、試作と実装、検証
