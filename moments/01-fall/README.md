# 見せ場 1: 下の層へ落ちる瞬間(段階 2 の最初の試作)

問い: 潜る瞬間と、深い層にいるときの空気が、音つきで気持ちいいか。あわせて、音の仕組みを kira に決めてよいかを、ここで聞いて決める
(2026-11-20 本人: 「最初の見せ場を見て決めるのが良い」)。

世界の作りは、実験 2c(`experiments/04-worlds/`)から引き継いだ。最初に足したのは音だけだったが、そのあと、ブリンクの動き、依存の線、世界の作り、体の決まりまで、ここで作り込んだ。下の節は、作った順の記録。**今の姿は、すぐ下の「今の姿」と「言葉」を見る。**

## 今の姿(2026-11-22)

- **体**: 重力があり、形は固い。歩く(5.5)・走る(Shift、9.5)・跳ぶ(F)。重力は、どの世界でも同じ。いちばん低い形の下が地面
- **ブリンク**(Space): 動き回る基本。前へ 80(移動キーを押していれば、その向きへ 40)。形の手前で止まる。形の天辺か、天辺のすぐ下の縁に当たると、その上に乗る。空中でも、何度でも使える
- **潜る・戻る**: 照準を合わせてクリック / E で潜る。右クリック / Q で戻る(出てきた形の上に立つ)
- **依存の線**: ふだんは見えない。照準を合わせた形の、影響の範囲(赤い光)と、頼っている先(白い光)だけが出る。その間、世界は暗くなる。線は、形の天辺の縁から出て、弧を描いて、相手の天辺の縁に入る。依存が世界の外へ続く形からは、空へ太い光が立つ(行き先がプログラムの外なら、明滅する)。依存の種類(呼び出し・読む・書く・型)で、線の姿が違う。循環も、たどって届いたときに初めて現れる
- **世界**: プロジェクト(柱)、`node_modules/` の街、ファイル(縦坑。起動で順に組み上がる)、関数(道)、ループ(輪になった道)
- **音**: 曲のパートが深さで減る・こもる・響く。潜る・戻る・ブリンク・足音・着地・落ちている間の風は、コードで作っている

## 音の作り

| 部分 | 中身 |
|---|---|
| 曲 | Suno で作った試しの曲(`dive-test-01`)の 7 パート。全パートを同じ拍から鳴らし続け、音量だけを動かす(実験 7 と同じ) |
| 深さ | 深いほど、パートが減り、こもって、響く。姿は `sound.rs` の表 `DEPTHS`(深さ 0〜3)で決めている |
| 離れる瞬間 | 曲が遠のく(0.5 秒でほとんど聞こえないところまでこもる)。落ちる音(高さが下がっていく音と風)が鳴る |
| 着く瞬間 | 1.1 秒かけて、その深さの音の姿になる。着地の低い音が鳴る |
| 戻るとき | 高さが上がっていく音。パートが戻り、こもりが晴れる |

落ちる音・浮かぶ音・着地の音・ブリンクの音は、コードで作っている(音のファイルは無い)。`SFX_DUMP=<フォルダ>` を付けて起動すると、WAV で書き出す。

2026-11-21 に作り直した(本人: 「もっとカッコいい音が良い」「瞬間移動は VALORANT のブリンクみたいな感じ」「効果音が BGM に比べて小さい」)。
世界を渡る音は 3 つを重ねる(頭の鋭い電子音 / 歪ませた低い音 / 高さが動く風)。ブリンク(Space)は 0.3 秒の短く鋭い音。曲は -11dB、効果音は 0dB。

| 深さ | 鳴らすパート | こもり具合 | 響き |
|---|---|---|---|
| 0 | 全部(7) | なし | 0.04 |
| 1 | synth, bass, drums, keyboard, strings | 5000 Hz | 0.16 |
| 2 | synth, bass, keyboard | 1800 Hz | 0.30 |
| 3 以上 | synth, bass | 700 Hz | 0.45 |

## ブリンクの動き(2026-11-21)

実験 2c では、Space を押した瞬間に位置が跳んでいた。本人: 「ブリンクは、瞬間移動中のアニメーションが欲しい」。

1 回目(駆け抜ける・視野が広がる・速さの線が流れる)は、本人「ダサすぎ。ここは電脳世界だよね?」。現実の乗り物の表現だった。消した。

2 回目(今の形)は、位置の情報が書き換わる動き(このときは「転送」と呼んでいた。今は、呼び名を「ブリンク」に統一している)。移動するのではなく、位置の情報が書き換わる。案は 4 つ出し(`docs/ideas.md`)、本人が「オススメで」と選んだ。

| 順 | 中身 | 数値(`main.rs` の先頭) |
|---|---|---|
| 1. ほどける | 世界の面が、手前から外へ消えて、線だけの骨組みになる。行き先へ、光の道が伸びる。この間は動かない | `UNMAKE_SEC` = 0.05 秒 |
| 2. 渡る | 線だけの世界を、光の道の上を一気に渡る。周りの形の輪郭が、赤い残像になって引きずられる | `CROSS_SEC` = 0.11 秒 |
| 3. 戻る | 着いた先で、面が手前から奥へ戻る。光の道と残像は薄れる。この間は、もう歩ける | `REMAKE_SEC` = 0.24 秒 |

本人(2026-11-21): 「アニメーションとしては非常にいい」。そのうえで 2 つ直した。

- 赤い枠 → **残像**: 出発点から見えていた周りの形の輪郭を、赤い写しにして 3 枚、進んだ分だけ引きずる(`draw` の中)
- 1 本の線 → **光の道**: 足元に 13 本の線が並び、真ん中ほど明るい。線ごとに速さの違う光の粒が、行き先へ流れる(`rail`)

残像は 6 枚(2026-11-21。本人の「もっと増やした方がいい」で 3 枚から 9 枚にし、「多すぎ。中間くらい」で 6 枚にした)。形の輪郭と、道が写しになる(頼っている相手へ伸びる線は、ふだん引かなくなったので、写しにもならない)。着いたあとは、後ろの写しから順に消えて、追いついてくる。色は赤一色のまま。

光の道は、残像と重なるとごちゃつくので、消した(2026-11-21。`R` で 道・細い・なし を見比べて、本人が「無くていい」と決めた)。

着いた瞬間にだけ、乱れ(グリッチ)を足した(2026-11-21。案は 5 つ出し、本人が「オススメで」と選んだ)。出発はきれいなまま残す。

- **座標が確定する**: 着いてから 0.1 秒、世界の線が粗い目盛りにずれ、3 段(見える範囲の 3% → 1.5% → 0.6%)で正しい位置に収まる
- **名前が化ける**: ブリンクの間、名前が記号に化け、着いてから 0.7 秒で頭から順に元の名前へ解ける。解け終わるまで、名前は赤い(最初は 0.2 秒で色も変えず、本人が「気付かない」と言ったので、延ばして赤くした)

`FREEZE=<秒>` を付けて起動すると、ブリンクの途中で時間を止められる(途中の絵を撮るため)。WSL で 3 場面を撮って、面が消えること・赤い線と枠が出ること・面が戻ることを確かめた。
動いたときの手触りは、本人の確認がまだ。

本人の感想(2026-11-21): 音は「物足りないけど、まだ検証だから、今はいい」。

## 影響の範囲(依存の線)

照準を合わせた形から、それに頼っている形へ、赤い線が 1 段ずつ(0.16 秒ごと)伸びていく。線が届いた形は輪郭が赤くなり、線の上を光の粒が同じ向きに流れる。左上に、壊れうる形の数が出る(`change it -> 4 may break`)。

「この形を変えたら、どこまで響くか」を、本物の依存関係からたどっている(2026-11-21。本人の「エンジニアが唸るのは？」に答えた案の一つで、本人が「8 も入れて」と選んだ)。誰にも頼られていない形(入口のファイルなど)では、何も出ない。

`TURN=<横>,<縦>` を付けると、撮る前に向きをその分だけ変えられる(照準を何かに合わせた絵を撮るため)。`TURN=-0.885,-0.42` で `src/log.ts` に合う。

頼っている相手へ伸びる線は、ふだんは引かない。照準を合わせたときだけ、その形の影響の範囲が出る(2026-11-21、本人が決めた)。

### 受ける側

照準を合わせた形が頼っている先(そこが変わると、この形が壊れうる)も、同じように 1 段ずつ伸びる。こちらは世界の線の色(赤ではない)で、粒は照準の形へ向かって流れる。左上に `relies on 5` のように数が出る(2026-11-21、本人の「受ける側も描くべき」で足した)。

- 赤: この形を変えると、壊れうる形(影響を与える先)
- 世界の線の色: この形が頼っている形(影響を受ける元)

## 循環(頼り合って輪になっている所)

互いに頼り合って輪になっている線は、ふだんは見えない。照準を合わせた形から線をたどって輪に届いたとき、初めて赤い輪として現れる(照準で探し出すもの)。明るさが息をするように揺れ、線の上を光の粒が終わりなく回り続ける。輪の中の形に照準を合わせると、左上に `!! circular dependency` と出る。起動したときに、どの世界に輪が何本あるかを出力する。

本人が「循環依存も表現して、それをシナリオにも組み込む」と決めた(2026-11-21)。最初は「循環は世界の傷なので、いつも見える」としていたが、本人が「普段は見えない方が良い。照準で探し出すのを、ストーリーに組み込める」と決め直した(2026-11-21)。シナリオでは、輪に入った崩壊は止まらずに回り続け、線を 1 本断って止める(これも本人が決めた)。

実験 1 の見本には循環が無いので、この見せ場用の見本 `sample/` を置いた。`src/` と `test/` は実験 1 の見本の写しで、`log.ts → config.ts → parse.ts → log.ts` の輪を足してある。`node_modules` は git に入れていないので、`cd moments/01-fall/sample && npm install` で用意する(近道(シンボリックリンク)で実験 1 の見本を指す形は、Windows から読めなかったので、やめた)。

```
cargo run -p fall -- moments/01-fall/sample
```

`AIM=<名前の一部>` を付けると、撮る前に、その形に照準を合わせられる(`AIM=store.ts`)。

## ファイルの世界: 縦坑(レビュー用のデモ)

本人の「ファイルの世界だけ雑」「今のは世界とは言えない」「レビューできる形にして」を受けて、案 A(縦坑)を土台に、B(起動)と C(中心の状態)を重ねた形を、実際に歩けるように作った(2026-11-21)。前の地層(果てなく続く板の階段)は、これに置き換えた。

- **形**: 中が空洞の塔。書かれたものは内側の壁から突き出て、書かれた順に、らせんを描いて下へ続く
- **種類で形が違う**: 関数は潜れる大きな塊、import は細い棒(上へ、霞の向こうへ線が伸びる)、型は線だけの枠
- **状態は中心**: `const` や `let` は、壁ではなく、空洞の中心の軸に浮かぶ
- **ケーブル**: 使う・呼ぶの関係は、空洞を横切る線になる。ふだんは見えず、照準を合わせたときだけ、影響の範囲として出る(本人が「全階層共通にした方が良い」と決めた。最初はいつも薄く見せていた)。循環も、照準でたどって届いたときだけ見える
- **起動**: 潜って 0.9 秒後から、書かれた順に上から現れる。現れた瞬間は赤く灯り、つながった線には赤い光が走る
- **壁**: すき間のある縦の板。すき間から外の霞が見える

まだ入っていない・粗いところ:

- ケーブルは、名前だけで調べている(A の中に B の名前が出てくれば「頼っている」)。同じ名前の別物を取り違えることがある
- import の線は、まだ本当の方角(頼っている相手のファイルがある向き)を向いていない
- `export` されたものが壁を突き抜けて外へ出る形、使われていないものが廃墟になる形は、まだ無い
- 中心の状態を「読む」「書く」の区別は、まだ無い

GO=store.ts cargo run -p fall -- moments/01-fall/sample    # src/store.ts の中から始める

### いつ動くかで、形を分ける

本人の「変数とかの定義はどう表現する？ 関数になってない処理とかも」への答えとして作った(2026-11-21。案を出し、本人が「それでつくって」と決めた)。

| 書かれたもの | いつ動くか | 形 |
|---|---|---|
| 関数 | 呼ばれるまで眠っている | 壁から突き出た塊(潜れる) |
| 関数の外の処理(`log("boot");` など) | 読み込まれたときに、一度だけ走る | **点火点**。らせんの線の上の小さな印。起動で順番が来ると、火花が四方へ飛び、呼んだ先へ光が走る。そのあとは、焼けた跡(中に × のある、線だけの枠)として残る |
| 変わらない値(`const INTERVAL = 60_000`) | 動かない | 中心の軸の、固い箱 |
| 起動で埋まる値(`const server = start()`) | 起動のときに、計算で入る | 最初は空の枠。光が呼んだ先へ行って戻ってくると、中身が入って面がつく |
| 書き換えられる値(`let runs = 0`、`[]` や `{}` で始まる入れ物) | あとから変わる | 中心の軸の箱から、外へ広がって消える枠が、ゆっくり繰り返す(脈) |

変数の見分けは、書き方だけで決めている(値に `(` があれば「起動で埋まる」、`const` でないか `[`・`{` で始まれば「書き換えられる」)。粗い見方で、取り違えることがある。

見本に、関数の外の処理を持つ `src/main.ts` を足した(`GO=main.ts` で、その中から始められる)。

## 体の決まりを、切り替えて比べる(2026-11-22)

本人: 「(潜る瞬間は)微妙。構造物の当たり判定とか、地面とか、重力の概念をどうするかがまだ何も考えてない」「これ難しいもんだいだよ」「C もやる価値があるんじゃない？」。
紙の上では決めず、同じ世界で 4 通りを切り替えて触れるようにした。キーの 1〜4 で、いつでも切り替わる(`BODY=1〜4` で、始めるときの決まりを選べる)。

| キー | 決まり | 中身 |
|---|---|---|

### 依存の種類を見分ける(2026-11-22。依存の線の 2 段目)

本人: 1 段目に「よくなった」。続けて、2 段目を作った。

**読み取り(`parse.rs`)**: 構文解析(oxc)の木を歩いて、節ごとに「宣言している名前」と「使っている名前と、その使い方」を集める。前は、名前が文字として出てくるかだけを見ていた。

| 依存の種類 | 見分け方 | 線の姿 |
|---|---|---|
| 呼び出し | `f()`、`obj.method()` | 細い光。粒が行って、戻る |
| 読む | 名前が出てくるだけ | 細い光。粒が、値の側から流れてくる |
| 書く | `x = …`、`x += …`、`x++`、`x.y = …`、入れ物の中身を変える呼び出し(`list.push()` など) | 太い光。粒が、値へ流れ込む |
| 型 | 型の位置にだけ出てくる | 点線の光。粒なし |
| 取り込み | import、package.json の依存(プロジェクトの世界と街) | 細い光。粒が、頼られる側から流れてくる |

同じ相手を何通りにも使っていたら、強いもの(書く > 呼び出し > 読む > 型)を残す。色は増やしていない(赤 = 影響の範囲、白 = 頼っている先)。

**線が出る世界が増えた**: 関数とループの世界にも、依存の線が出る(文が、前の文で宣言した変数を使っている、など)。

**空への光**: 形が、その世界の外で宣言された名前を使っていれば、空へ光が立つ(関数の中から、ファイルの関数や変数、import した物を使う文)。ファイルの世界では、import の形から立つ。
行き先がプログラムの外なら、光が不規則に明滅する。プログラムの外 = `fetch`・`process` などを直に使う / Node.js のファイル・ネットワーク・プロセスのモジュール(`fs`、`http`、`child_process` など)から import した名前を使う。

画面の左上に、照準の形がじかに頼っている先の内訳(`calls 1  reads 2  writes 1`)と、行き先(`-> another world` / `-> outside the program`)が出る。
`LINKS=1` を付けて起動すると、全部の世界の依存の線を文字で出す(確かめるため)。

分かっている粗さ:
- 名前だけで結んでいる(名前が指す先までは調べていない)。同じ名前の別の物を取り違える(例: `const Config` と `type Config`)
- 関数の引数や、`for (const f of …)` の変数は形になっていないので、線の相手にならない
- `console.log` は、プログラムの外に数えていない(数えると、ほとんどの関数が明滅する)
- 関数の世界では、依存の線の弧が門の上を通るので、道に立つと見上げないと見えにくい
- 空への光は、どこへ続いているか(どのファイルか)までは示さない

確かめたこと(WSL): `LINKS=1` の出力を全部の世界で読んで、種類と行き先が合っていること / 縦坑で、白い光(頼っている先)と赤い光(影響の範囲)が種類ごとの姿で出ること / 関数の世界で、空への光が立つこと。Windows の実機では、まだ見ていない。
